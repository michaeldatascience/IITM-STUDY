0. Why does tokenization even exist?

The naive options both fail:

Word-level tokenization ("split on spaces"): vocabulary explodes. English alone has hundreds of thousands of word forms once you count plurals, tenses, typos, proper nouns. Any word not seen during training → <UNK>. Model sees "run", "running", "runs" as three *completely unrelated* IDs — no shared structure.

Character-level tokenization: vocabulary is tiny (~100 symbols), zero OOV problem. But now a sentence that was 10 words becomes 50 characters. Since a Transformer's self-attention cost grows quadratically with sequence length, and each token carries very little meaning, the model has to work far harder to reconstruct "this is a word" from scratch every time.
Think of it like packing a suitcase. Word-level tokenization is packing every possible outfit combination pre-assembled — you need infinite suitcases. Character-level is packing individual threads — you need almost no suitcases, but now you have to reassemble every shirt by hand each time you want to wear one. Subword tokenization packs reusable pieces: collars, sleeves, buttons — common enough to reuse across outfits, big enough that you're not stitching from thread.
The subword insight (the thing every method below is chasing): frequent chunks of text should get their own token ("ing", "the", "##ed"), rare chunks should decompose into smaller frequent pieces, and in the worst case you always fall back to characters/bytes — so OOV becomes mathematically impossible. Every method below is really just a different answer to one question: which chunks deserve to be a single token, and how do I decide?

1. Byte-Pair Encoding (BPE)

Motivation: BPE was originally a 1994 data-compression algorithm (repeatedly replace the most frequent byte pair with a new byte). Sennrich et al. (2016) repurposed it for NLP: instead of compressing bytes, repeatedly merge the most frequent adjacent symbol pair in your corpus into a new symbol. Do this enough times and you've built a vocabulary that's exactly tuned to the statistics of your training data — frequent words survive whole, rare words get chopped into meaningful pieces.

Algorithm (rigorous)

1. Initialize vocabulary = every individual character/byte in the corpus.
2. Represent each word as a sequence of symbols (start = characters), track word frequencies.
3. Count frequency of every adjacent symbol pair across the whole corpus (weighted by word frequency).
4. Merge = pick the pair (a, b) with max count. Replace every occurrence of "a b" with new symbol "ab". Add "ab" to vocabulary.
5. Repeat steps 3–4 for a fixed number of merges (a hyperparameter — this + base alphabet size determines final vocab size).
where: pair count(a,b) = Σ over words containing "a" immediately followed by "b" of (word frequency). Purely frequency-driven — no probability model, no likelihood, just counting.

Key property to internalize: BPE is greedy and frequency-only. It never looks ahead, never asks "does this merge improve my language model," it just asks "what pair is most common right now." This greediness is both its strength (cheap, deterministic, fast) and its weakness (can lock in a merge early that isn't globally optimal) — this is exactly the gap WordPiece tries to close.

def get_pair_counts(word_freqs):
    pairs = Counter()
    for word, freq in word_freqs.items():
        for i in range(len(word) - 1):
            pairs[(word[i], word[i+1])] += freq
    return pairs

def merge_pair(pair, word_freqs):
    a, b = pair
    merged = a + b
    new_word_freqs = {}
    for word, freq in word_freqs.items():
        new_word = []
        i = 0
        while i < len(word):
            if i < len(word)-1 and word[i]==a and word[i+1]==b:
                new_word.append(merged)
                i += 2
            else:
                new_word.append(word[i])
                i += 1
        new_word_freqs[tuple(new_word)] = new_word_freqs.get(tuple(new_word),0) + freq
    return new_word_freqs

2. WordPiece

Motivation: WordPiece (Google, used in BERT) asks: what if raw frequency isn't the right merge criterion? Two symbols "t" and "h" might co-occur a lot simply because "t" and "h" are both extremely common individually (in "the", "that", "this"...) — not because "th" as a unit is special. WordPiece instead merges the pair that gives the biggest boost in language-model likelihood — i.e. the pair that co-occurs *more than you'd expect from chance* given how common each symbol is on its own.

Math — the scoring function

score(a, b) = freq(a, b) / ( freq(a) × freq(b) )
where:
• freq(a,b) = count of symbol pair (a,b) occurring adjacently (same as BPE's pair count)
• freq(a) = total count of symbol "a" appearing anywhere in the corpus (not just in this pair)
• freq(b) = total count of symbol "b" appearing anywhere
This is literally pointwise mutual information (unnormalized) — it rewards pairs that appear together far more than their individual frequencies alone would predict.
BPE asks "how often do 'peanut' and 'butter' appear next to each other, in absolute terms?" WordPiece asks "given how common the words 'peanut' and 'butter' individually are, is their co-occurrence surprising?" Two very rare words that ALWAYS appear together (high mutual info, low raw frequency) get prioritized by WordPiece but might lose to a merge like "the a" under raw-frequency BPE simply because "the" and "a" are both extremely common words individually.

Under raw BPE, (e,s) and (s,t) were tied leaders at count 9. Under WordPiece scoring, (l,o) wins outright at 0.1429 — because "l" and "o" are individually rare (only appear together, essentially), so their co-occurrence is maximally "surprising." BPE would never have picked (l,o) first since its raw count (7) is lower than (e,s) or (s,t)'s count (9).
This is the single most important distinguishing fact between BPE and WordPiece — memorize the formula, not just the vibe. BPE merge rule: argmax freq(a,b). WordPiece merge rule: argmax freq(a,b)/(freq(a)·freq(b)). Everything else (build vocab from chars, merge repeatedly, save merge history) is identical.

Inference-time difference: WordPiece uses greedy longest-match, not merge-replay

BPE applies its saved merges in learned order at inference. WordPiece instead does greedy longest-suffix matching: for a new word, find the longest prefix that's in the vocabulary, split it off, then repeat on the remainder. Continuation subwords are marked with ## (BERT's convention) to indicate "this piece is NOT a word start." Example: tokenizing "widest" with vocab {"wi","##dest","##d","##est","w"} → greedy match finds "wi" (longest prefix in vocab) then "##dest" → ["wi", "##dest"].

def wordpiece_score(pair, pair_counts, symbol_counts):
    a, b = pair
    return pair_counts[pair] / (symbol_counts[a] * symbol_counts[b])

def get_symbol_counts(word_freqs):
    counts = Counter()
    for word, freq in word_freqs.items():
        for sym in word:
            counts[sym] += freq
    return counts

3. Unigram Language Model Tokenization

Motivation: BPE and WordPiece both build UP from characters, merging greedily — once a merge happens, it's permanent, never revisited. Unigram LM flips the whole strategy: start with a huge candidate vocabulary (e.g. all substrings up to some length, or a BPE-trained large vocab), then iteratively prune down to the target size by removing whichever tokens hurt the corpus likelihood the least. It's top-down instead of bottom-up, and probabilistic instead of greedy-count-based.
BPE/WordPiece are like building a Lego tower by snapping bricks together one pair at a time and never taking any back off. Unigram LM is like starting with a giant pile of every possible brick combination, building the tower, then removing whichever bricks you can pull out without the tower losing structural integrity — repeat until you hit your target brick count.

Math

P(x) = Π P(x_i)     for a segmentation x = (x_1, ..., x_n) of a word/sentence into subword units, assuming each token is generated independently ("unigram" = no context between tokens, hence the name). Best segmentation: x* = argmax over all possible segmentations Σ, of Π P(x_i) Training objective (given fixed vocab V with token probabilities P(x_i)): maximize   L = Σ over all words w in corpus, log P(w)  =  Σ_w log( Σ_{x∈segmentations(w)} Π P(x_i) )
where:
• P(x_i) = probability assigned to subword token x_i, estimated via EM (Expectation-Maximization)
• segmentations(w) = every possible way to split word w into pieces from vocabulary V
• the inner sum over segmentations is efficiently computed with the forward-backward algorithm; the argmax best single segmentation is computed with the Viterbi algorithm — same dynamic programming tools you'll meet again in HMMs/CRFs

Pruning loop (training)

1. Seed a large vocabulary (e.g. 10× target size) — commonly via a suffix-array frequency scan or a BPE pre-pass.
2. E-step: run Viterbi/forward-backward to get expected usage of each token given current probabilities.
3. Compute, for each token, "loss if removed" = how much the corpus log-likelihood would DROP without it (its pieces would have to be covered by smaller sub-tokens instead).
4. Remove the bottom X% of tokens by that loss score (i.e. remove tokens whose absence barely hurts likelihood).
5. Re-estimate probabilities (M-step), repeat from step 2 until vocab hits target size.

Worked intuition on our corpus

Suppose our seed vocabulary already contains: {l, o, w, e, r, n, s, t, i, d, _, lo, low, es, est, wi, ne, new}. For the word "lower", two candidate segmentations exist: ["low","e","r","_"] vs ["l","o","w","e","r","_"]. Since "low" is a high-probability token (it covers "low"(5) + is a prefix of "lower"(2) = strong evidence in the corpus), P(["low","e","r","_"]) ≫ P(["l","o","w","e","r","_"]) — the model's own probabilities pick the more "chunked" segmentation automatically, via Viterbi, no hand-written rule needed. Now ask: does the token "ne" (from "newest") pay for itself? If removing "ne" only costs a tiny likelihood drop (because "n" and "e" individually already do a fine job, or "new" already covers it), Unigram prunes "ne" away — even though a greedy bottom-up method might never have proposed removing something it already built.
Crucial property: because Unigram is probabilistic, tokenization at inference time isn't deterministic-by-rule the way BPE's merge-replay is. The SAME word can (in principle, with sampling) be segmented multiple valid ways — this is exploited deliberately for subword regularization: during training, randomly sample a few different valid segmentations of the same word as a form of data augmentation, making the downstream model robust to tokenization noise.

def viterbi_segment(word, vocab_logprob):
    n = len(word)
    best_score = [-math.inf]*(n+1)
    best_score[0] = 0.0
    backptr = [None]*(n+1)
    for end in range(1, n+1):
        for start in range(0, end):
            piece = word[start:end]
            if piece in vocab_logprob:
                score = best_score[start] + vocab_logprob[piece]
                if score > best_score[end]:
                    best_score[end] = score
                    backptr[end] = start
    tokens = []
    pos = n
    while pos > 0:
        start = backptr[pos]
        tokens.append(word[start:pos])
        pos = start
    return tokens[::-1]

4. SentencePiece — not a 4th algorithm, a framework

Common confusion to kill right now: SentencePiece is NOT a competing algorithm alongside BPE/WordPiece/Unigram. It's a language-agnostic implementation/framework that can run EITHER the BPE algorithm OR the Unigram LM algorithm underneath (you pick via a flag: --model_type=bpe or --model_type=unigram). What makes it its own named "thing" is a set of engineering decisions about the preprocessing layer, not the merge/scoring math.

What SentencePiece actually changes

1. No language-specific pre-tokenization. Classic BPE/WordPiece assume you already split on whitespace before running the algorithm (that's how "word boundary" was defined in our worked examples above). This silently assumes whitespace = word boundary — true for English, false for Japanese/Chinese/Thai which don't use spaces between words. SentencePiece treats the raw input string directly, spaces included, as just another sequence of Unicode characters.

2. Whitespace becomes a visible symbol. SentencePiece replaces every space with a special meta-symbol, conventionally ▁ (U+2581), BEFORE running BPE/Unigram on the raw string. So "low er" (with an explicit space) tokenizes completely differently from "lower" (no space) — and critically, detokenization becomes lossless and reversible: you can always tell where spaces were, because they're literal tokens in the vocabulary, not implicit boundaries you have to guess at.

3. Fully reversible / lossless normalization. Because nothing is thrown away (no whitespace-splitting assumption baked in), decode(encode(x)) == x exactly, for any input, in any script.
Same corpus concept, SentencePiece style: instead of pre-splitting into the word "lower", SentencePiece would see a raw stream like ▁l▁o▁w▁e▁r — wait, more precisely, it converts "the lower box" into "▁the▁lower▁box" treating the leading/internal spaces as the symbol ▁, THEN runs BPE or Unigram merges on THAT character stream, so ▁ can merge with adjacent letters just like any other symbol (e.g. "▁l" + "ow" → "▁low" becomes a plausible learned token, meaning "start-of-word low").
Exam-relevant distinction: our worked BPE/WordPiece examples above used the _ marker for END-of-word. Real SentencePiece uses ▁ for what's effectively START-of-word (attached to the following token) — this asymmetry (end-marker vs start-marker convention) trips people up. Different tokenizer implementations pick different conventions; always check which one a given paper/library uses rather than assuming.

5. Byte-level BPE (GPT-2 / GPT-3 / GPT-4's tiktoken)

Motivation: Even with subword tokenization, if your base vocabulary is Unicode characters, you still have an OOV problem — Unicode has 149,000+ characters (emoji, rare scripts, etc.), and however comprehensive your training corpus, some character combos will be unseen at inference. Byte-level BPE closes this gap completely by using a base alphabet of exactly 256 possible byte values (every possible byte, 0x00–0xFF) instead of "every possible character." Since ANY Unicode string can be encoded as UTF-8 bytes, and there are only 256 possible byte values, the base vocabulary is complete by construction — zero OOV is mathematically guaranteed, not just empirically likely.
Character-level BPE's base alphabet is like keeping every language's alphabet in your toolbox — you need a new tool the moment you meet a script you didn't stock. Byte-level BPE's base alphabet is like keeping a box of exactly 256 LEGO unit-bricks — genuinely ANY shape, in any language, in any emoji, can be built from combinations of those same 256 bricks. Nothing new is ever needed.

Mechanism

1. Encode input text as UTF-8 bytes: text → bytes (each byte is an integer 0–255).
2. Base vocabulary = all 256 byte values, each treated as its own initial "character" for BPE purposes.
3. Run standard BPE merges (exactly the algorithm from Section 1) directly on the byte sequence, not on Unicode characters.
where: a single Unicode character can be MULTIPLE bytes (e.g. "€" is 3 bytes in UTF-8: E2 82 AC) — so byte-level BPE might initially represent one emoji as 4 separate "characters" (bytes) before merges recombine them into a single learned token, if that emoji appears often enough in training.

8. Flashcards for spaced repetition (add to your boxes)

Q:
BPE merge rule?
A: argmax over pairs of raw adjacent-pair frequency, freq(a,b).
Q:
WordPiece merge rule?
A: argmax of freq(a,b) / (freq(a)·freq(b)) — mutual-information-like score, not raw count.
Q:

A: Top-down: start with a large candidate vocab, prune tokens whose removal costs the least corpus likelihood.
Q:

A: Viterbi (dynamic programming over all possible segmentations).
Q:

A: Base vocabulary = all 256 possible byte values; any Unicode string is representable as UTF-8 bytes, so every input decomposes into known symbols.

A: Greedy longest-prefix-match against the vocab, marking continuation pieces with ## (not a merge-replay like BPE).
